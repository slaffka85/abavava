# chat-abavava — план проекта (v1)

Документ ведёт руководитель проекта: объём, критерии приёмки, статус этапов, риски.

## 1. Цель продукта

Рабочий мессенджер, в котором два пользователя могут обменяться текстовыми сообщениями
в реальном времени и совершить аудио/видео звонок, разворачиваемый одной командой и
готовый к развитию (групповые чаты, вложения, групповые звонки).

**Критерий успеха v1:** пользователь регистрируется, находит собеседника, ведёт с ним
переписку с индикаторами присутствия/набора/прочтения и совершает звонок; всё это
разворачивается через `docker compose up --build` и проверяется автотестами.

## 2. Объём v1

### В объёме

| Область | Содержание |
|---|---|
| Аккаунты | email + пароль, JWT access/refresh, ротация refresh, отзыв сессий, профиль, поиск пользователей |
| Диалоги | личные (идемпотентно) и групповые (до 64 участников, роли владелец/участник) |
| Сообщения | текст до 4000 символов, доставка по WS, история с keyset-пагинацией, счётчики непрочитанного, отметки прочтения, идемпотентность по `client_id` |
| Реальное время | одно соединение на устройство, мультидевайс, присутствие для контактов, индикатор набора, heartbeat, реконнект с догоном состояния |
| Звонки | аудио/видео 1:1, WebRTC perfect negotiation, сигналинг по WS, таймаут дозвона, история, ICE-конфигурация (STUN/TURN) |
| Интерфейс | авторизация, двухпанельный мессенджер, тред, composer, модалка нового чата, панель участников, оверлей звонка, входящий звонок, история звонков, тосты, адаптив до 360 px |
| Инфраструктура | docker-compose (postgres + api + web), Dockerfile'ы, nginx с прокси WS, .env.example, миграции |
| Качество | unit-тесты, интеграционные и E2E-тесты на реальной БД, смоук-инструмент для развёрнутого стенда, документация |

### Вне объёма v1 (сознательно)

Групповые звонки (нужен SFU), вложения и файлы, редактирование/удаление сообщений,
загрузка аватаров, демонстрация экрана, push-уведомления, end-to-end шифрование,
поиск по истории сообщений, модерация и админка, мобильные приложения, федерация.

## 6. Риски

| Риск | Влияние | Вероятность | Что сделано / что делать |
|---|---|---|---|
| Звонки не соединяются в мобильных сетях | высокая | высокая | в v1 задокументировано; в v1.1 — TURN (coturn) в compose и выдача временных креденшелов через API |
| Регрессии в медиапути (WebRTC) | средняя | низкая | покрыто проверкой в реальном браузере (`npm run media:check`, 33 проверки); в CI запускать на агентах с браузером |
| Стоимость bcrypt (cost 12) на всплесках входов | средняя | низкая | rate limit на `/auth/*`; при росте — вынести хеширование в отдельный пул воркеров или снизить cost по SLA |
| Масштабирование WebSocket на несколько инстансов | высокая | средняя | sticky sessions на балансировщике; далее Redis Pub/Sub за интерфейсом `domain.Broadcaster` |
| Рост таблицы `messages` | средняя | средняя | keyset-пагинация и индексы уже есть; далее партиционирование по `created_at` |
| Утечка refresh-токена | высокая | низкая | хранится только хеш, ротация, отзыв всех сессий при повторном использовании |
| Устаревание схемы | средняя | низкая | миграции версионированы, применяются под advisory-локом, откат — новая миграция |

## 7. Качество и соглашения

- **Тесты как контракт:** каждое требование из §3 имеет автоматическую проверку; E2E
  работают на реальной PostgreSQL, моков нет.
- **Изоляция тестов:** отдельная база на тест, с проверкой `current_database()` —
  инфраструктурный баг, при котором тесты работали в общей базе, был найден и закрыт.
- **Ошибки:** единый формат `{error:{code,message,details}}` для REST и WS; внутренние
  детали не покидают сервер (`internal` без текста причины).
- **Права:** проверка участия в диалоге раньше валидации тела — посторонний не узнаёт
  о существовании ресурса.
- **Идемпотентность:** на уровне уникальных индексов БД, а не логики клиента.

## 8. Следующие шаги (приоритет)

1. **TURN-сервер** в compose + выдача временных креденшелов — без этого звонки
   ненадёжны в мобильных сетях (оценка: 1–2 дня).
2. **Метрики Prometheus** (`/metrics`) и запуск `media:check` в CI — эксплуатация и
   защита от регрессий медиапути (оценка: 1 день).
3. **Redis Pub/Sub для рассылки** — горизонтальное масштабирование без sticky sessions
   (оценка: 2–3 дня).
4. **Вложения** — объектное хранилище, лимиты, антивирусная проверка (оценка: 4–5 дней).
5. **Групповые звонки** через SFU (LiveKit/Pion) — отдельный медиасервер, новая модель
   участников (оценка: 2–3 недели).
