# chat-abavava-java — команда параллельной разработки (Java-трек)

Второй бэкенд chat-abavava. Тот же продукт, тот же контракт, независимая
реализация: **Java 26 + Spring Boot 4.1 + Spring Data JDBC** вместо
Go 1.25 + net/http + pgx. Цель — две команды развивают один и тот же продукт
параллельно, а клиент (React SPA) работает с любым бэкендом без изменений.

## Зачем два бэкенда

- **Контракт проверяется делом.** REST `/api/v1` и WebSocket-протокол v1
  описаны в `chat-abavava/docs/API.md` и `docs/WS-PROTOCOL.md`. Вторая
  реализация — самая честная проверка того, что спецификация полная:
  всё, что не описано, обязательно «вылезет» при паритетных тестах.
- **Независимая эксплуатация.** Оба трека можно запустить одновременно
  (Go на `:8080`, Java на `:8082`) и сравнивать поведение.
- **Технологическая страховка.** Понимание цены решения (латентность,
  стоимость хеширования, объём кода) без переписывания продакшена.

## Состав команды

| Роль | Ответственность | Артефакты |
|---|---|---|
| **PO / продукт** | Приоритеты, приёмка паритета, решения о расхождениях | Этапные отчёты, приёмка smoke |
| **Трек-лид (Java)** | Архитектура трека, фундамент, интеграция модулей, сборка | `config/`, `domain/`, `http/`, `security/`, `contract/` |
| **Backend A — Chat** | Диалоги, сообщения, участники, пагинация, идемпотентность | `chat/` (ChatService, ChatRepository, ConversationController) |
| **Backend B — Calls** | Состояния звонков, таймеры дозвона, история, сигналинг-транзит, ICE | `call/` |
| **Backend C — Realtime** | WebSocket-транспорт, presence, протокол v1, heartbeat | `realtime/` |
| **QA / паритет** | Smoke/E2E обоих бэкендов, матрица паритета | `docs/PARITY.md`, прогоны `cmd/smoke` |

Правило интерфейсов: `contract/*.java` — единственная точка стыковки модулей.
Интерфейсы объявляются до старта параллельных работ и после этого не меняются
без согласования трек-лида.

## Как устроена параллельная работа

1. **Контракт-первый.** Контракт — это документы Go-трека (`docs/API.md`,
   `docs/WS-PROTOCOL.md`) и схема БД (`migrations/0001_init.sql`). Изменение
   контракта возможно только синхронно в обоих треках.
2. **Фундамент первым.** Трек-лид собирает каркас (config/db/domain/security/
   http/contract) и доводит его до зелёной сборки. Только после этого
   модули раздаются параллельно.
3. **Модули — независимые пакеты.** Chat, Call, Realtime не импортируют друг
   друга; связь — через `contract/*` и Spring-бины. Это позволяет вести три
   модуля параллельно без merge-конфликтов.
4. **Сборка — у трек-лида.** Инженеры не запускают Maven в общем дереве:
   `mvn -o package` — на воротах интеграции (иначе параллельные сборки
   конфликтуют).
5. **Ворота качества.** Каждая итерация заканчивается:
   `build.ps1 check` → поднятая PostgreSQL → `cmd/smoke` (Go) против Java-API.
   Smoke-тест Go-трека — внешний чёрный ящик: он ничего не знает о Java-коде
   и проверяет именно контракт.

## Как запускать оба трека одновременно

```powershell
# Go-трек (как раньше)
cd chat-abavava && docker compose up -d postgres

# Java-трек: своя БД на 5433, приложение на 8082
cd chat-abavava-java
docker compose up -d postgres
powershell -ExecutionPolicy Bypass -File build.ps1 run
```

`ABV_DATABASE_URL` можно направить на БД Go-трека (порт 5432, схема
применяется миграциями в обоих кодбазах одинаково): Java-трек ожидает
JDBC-URL (`jdbc:postgresql://localhost:5432/abv?sslmode=disable`, логин/пароль
abv — через `ABV_DATABASE_USERNAME`/`ABV_DATABASE_PASSWORD`), Go-трек —
`postgres://...`. Оба сервиса будут работать с одними и теми же данными —
удобно для A/B-проверки.

## Границы ответственности

- Go-трек — эталон поведения; при расхождении приоритет у `docs/API.md`
  и `docs/WS-PROTOCOL.md`, затем у наблюдаемого поведения Go.
- Java-трек не меняет контракт задним числом: сначала изменение в
  документах/схеме, затем реализация в обоих треках.
- Идентификаторы ошибок, HTTP-коды, формы JSON — строго паритетны (см.
  `docs/PARITY.md`). Свободны: внутренняя структура пакетов, способ
  сериализации дат (RFC3339), реализация таймеров.
